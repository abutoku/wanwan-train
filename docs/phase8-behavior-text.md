## 1. タップ移動の挙動変更

### 変更前

`travelTo` → `_runTravel` が目的地まで **1駅ずつ** `_hop`（900ms走行）し、
駅間で `HOP_PAUSE_MS`（250ms）ポーズしていた。Train 側は `currentIndex` の
±1 の変化ごとに1駅ぶんのアニメーションを実行。

### 変更後

`_runTravel` は `currentIndex` を **目的地へ一度に** 更新し、移動距離に応じた
時間だけ待つ。Train 側は複数駅ぶんの移動を **1本の連続アニメーション**
（easeInOut）で描画するため、途中駅で減速・停止しない。

- 所要時間: `travelDurationMs(hops) = STEP_MS + (hops - 1) * TRAVEL_EXTRA_MS`
  - 1駅なら従来どおり 900ms、2駅目以降は1駅あたり 320ms 加算
  - 遠距離（山手線半周 ≒ 14駅）でも約5秒に収まる「急行」感
- `HOP_PAUSE_MS` は不要になったため削除
- ▶（1駅進む）/ ◀（1駅戻る）ボタンと自動再生は従来どおり1駅ずつ

### Train.tsx のアニメーション

従来は「インデックス差分 ±1」を前提にした相対アニメーションだった。
複数駅ジャンプに対応するため **絶対座標ターゲット** 方式に変更:

- 直線路線: `target = currentIndex`
- 環状線: タップ移動中（`destinationIndex` あり）は選択中の `direction`
  （内回り/外回り）に従って周回し、store の `stopsBetween` と一致させる。
  ボタン操作（±1）は従来どおり最短方向。
  いずれも現在の実位置 `pos.get()` から mod 計算で絶対ターゲットを算出
  ※「±1は最短・それ以外は方向準拠」という差分ベースの判定だと、走行中に
  1駅手前へ差し替えたとき（差分が n−1）に store は「方向のまま周回」
  なのに Train が「1駅逆走」と解釈して食い違う。検証でこの不整合を検出し、
  `destinationIndex` の有無で判定する方式にした
- 走行中に別の駅がタップされた場合も、現在の実位置から新目的地へ
  そのまま滑らかに接続する（相対方式だと位置がずれるのを防ぐ）
- アニメーション時間は store の `travelDurationMs` を共用し、
  状態更新の待ち時間と描画を同期

### 影響範囲

- `currentIndex` は「走行中 = 次に着く駅」の意味を維持
  （一気に進むため、走行中の案内表示は目的地＝次の停車駅になる。急行の挙動として自然）
- 乗り換え（`transferTo`）はマップが `key={lineId}` で再マウントされるため影響なし

## 動作確認（実施済み）

Playwright + store 購読ログで以下を確認した。

- `npm run build`（tsc --noEmit + vite build）が通る
- 山手線 東京→品川（6駅）: `currentIndex` が一度に 0→6 になり、
  2500ms（= 900 + 5×320）の1本のアニメーションで途中停車なく到着。到着演出も正常
- 走行中の差し替え: 渋谷へ走行中に恵比寿をタップ → 外回りのまま周回して到着し、
  store の待ち時間（29駅 = 9860ms）とアニメーションの到着タイミングが一致
- 直線路線（東横線）: 後方の駅タップで方向が自動で rev に切替、
  4駅 = 1860ms / 8駅 = 3140ms の1本のアニメーションで到着
- ▶ / ◀ ボタンは従来どおり1駅ずつ（900ms・最短方向）
- タイトル画面の文言が上表のとおり表示される
